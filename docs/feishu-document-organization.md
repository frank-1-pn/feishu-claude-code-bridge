# 按 Bot 场景整理文档和收到的文件

文件接收层负责保存原件、原文件名、来源与哈希；对应 Codex 会话负责真正读取内容、分类和整理。两者的完成状态明确分开，不把文件下载成功称为知识库入库或云空间归档。

## 默认行为

私有 binding 可设置：

```json
{
  "document_organization": {
    "version": 1,
    "enabled": true,
    "default_destination": "vault",
    "bare_file_action": "organize"
  }
}
```

`default_destination` 支持 `vault`、`project`、`feishu`；`bare_file_action` 支持 `organize` 或 `preserve`。未配置/显式关闭时保持原有行为。配置只从本地 binding 读取，文件内容不能设置。当前用户选择的部署策略是知识库 Bot 默认本地入库；编程 Bot 默认项目附件区，明确要求时才归档到飞书。实际 bot/profile/thread 映射不写入仓库。

用户只发送附件时执行默认整理；当次分析、修改、排错、指定去向或暂不整理等指令优先。归档原件与正文/代码任务分别处理，不因收到编程截图就额外建立知识库笔记。

## 数据与恢复

下载仍使用现有资源接口与 50 MiB 限制。下载缓存增加可取得的原文件名；`document-intake.json` 记录当前绑定、项目、来源消息、文件路径/大小/SHA-256 和接收时的路由规则。原文件名缺失时不伪造，在实际复制时使用下载文件名作可用名称。

知识库模式只写私有入站清单，不由 bridge 绕开 vault 的锁、worker、单来源笔记、唯一集成者和 manifest-last 流程。接收后自动把整理规则交给原 Codex 会话，按 `feishu-bot-runtime/references/document-organization.md` 继续。

项目模式在当前 workspace 下的 `.feishu-attachments/` 保存原件，先建立忽略全部内容的局部 `.gitignore`，避免私有文件随普通 Git 操作提交。按 bot、项目与线程隔离目录，内容按哈希存储，来源按消息独立记录；同内容同文件名复用副本，仍保留每次收件来源。项目源码不改，归类记录和索引由会话完成。已存在但内容不同的原件、损坏清单、变化的策略或目录 junction 逃逸均不覆盖；归档准备失败会说明错误，但已正常下载的文件仍交给会话处理。

已有入站记录不自动重放，已有文件也不批量补归档。新规则仅作用于升级后尚未准备的文件消息。音频/视频的原流程和关闭的 ASR 不变。

## 云归档边界

明确要求云归档时由对应会话调用现有飞书文件/文档工具，核对 bot 身份、目标目录与绑定用户权限，保留本地原件，分别验证原件上传和整理后的云文档。原生文件上传、文件夹权限的真实验收须在该 bot 的具体任务中完成；仅配置默认规则不表示云上传已经测试通过。

本次不新增云空间后台上传队列，也不自动把编程附件传到云端。`drive +upload` 自动给 CLI 当前用户授予 full_access 的行为不能替代当前绑定的权限核验。收到的文件、清单和真实云资源标识都不属于桥接代码 GitHub 同步范围。

## 验证

针对性测试覆盖原件字节/文件名保留、下载缓存及重试、同内容来源分离、跨 Bot/项目/线程隔离、原件篡改、损坏记录、规则改变、目录 junction、Windows 文件名、配置关闭和归档失败后的正常消息交付。测试产物只在临时 fixture 中生成，不制造用户知识库笔记。

2026-09-28 验证：全套 280 项测试通过，0 失败、0 跳过。另复用本轮早先发送的专用 TXT 验收附件，真实调用飞书资源下载，再在临时工作目录验证原文件名、完整字节/SHA-256、项目原件副本、重复准备只下载一次及单条来源记录；没有写真实知识库或编程项目，也未注入虚构用户请求。

自动内容分类仍由原会话的 agent 执行，需要真实附件进入会话后核对产物与最终回包；不能用接收层单元测试或运行时健康代替该项验收。
